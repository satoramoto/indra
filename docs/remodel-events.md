# Goals workflow event delivery

The `goals-v1` Team Lead, Product and Developer entry points run finite turns. Their processes wait on sockets or filesystem notifications between turns. The historical polling entry points remain only for teams without the explicit workflow discriminator. Enabling the new model requires the Scheduler, Developer, Product and Surfaces implementations and the setup below. Missing Developer/Product capabilities fail visibly; no legacy execution fallback starts new-model work.

This change implements delivery. It does not configure a repository webhook, expose a listener publicly, retrieve a real secret during installation, change permissions, or start Indra. The repository had no webhook and lacked sufficient automatic-merge protection when the remodel was implemented.

## One-time setup

1. Store a webhook signing secret in 1Password and grant the existing Indra service account access to that field. Keep the secret out of command arguments, environment variables, Git and logs. The receiver reads it into memory with the existing `opRead`/staged service-account path when the bridge starts.
2. In the local `<state-checkout>.runtime/workflow-delivery.json`, configure only its reference and an unused loopback port. The file has exactly these fields (replace the reference with the actual non-secret item reference):

   ```json
   {"version":1,"port":9781,"secretRef":"op://VAULT/ITEM/FIELD"}
   ```

   Keep the runtime directory private. This file is runtime configuration, never part of the state repository. Ports must be integers between 1024 and 65535. A missing or invalid file stops the new-model bridge with this document's setup instruction.
3. Provide owner-managed HTTPS forwarding to `http://127.0.0.1:9781/indra/github` on the machine running Indra. The built-in receiver binds only `127.0.0.1`; there is no public bind option or relay service. Forward the exact raw body and `X-Hub-Signature-256`, `X-GitHub-Delivery` and `X-GitHub-Event` headers. Choose and operate the HTTPS forwarding infrastructure separately; Indra does not create one.
4. Configure a GitHub repository webhook at that HTTPS URL, with JSON content, the same secret, certificate verification enabled, and these events: **Pull requests**, **Pull request reviews**, **Check runs**, **Check suites**, and **Statuses**. Pull-request changes deliver conflicts/new heads and actual merges; reviews and check/status deliveries wake current-head verification. The GitHub `ping` delivery is accepted without scheduling work. See GitHub's [delivery handling](https://docs.github.com/en/webhooks/using-webhooks/handling-webhook-deliveries) and [signature verification](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) documentation.
5. Preserve the bot's normal access to its state-configured Mattermost team home and `GET /api/v4/websocket`. The existing `planning serve --state PATH` / `planning host --state PATH` commands start Chick's bridge; `seat run --seat SEAT_ID --state PATH` starts a Product or Developer consumer. The current bridge entry selects Chick's Yahaha team, then derives its project and home channel from state. No channel/project prompt override is accepted.
6. Before unattended merges, configure the exact supported server-enforced review/CI policy in [remodel-contract.md](remodel-contract.md), including main and sprint target branches. A readable but insufficient policy remains an actionable merge blocker. The immediate SHA-bound merge gate never arms deferred auto-merge or bypasses protection. This document does not authorize permission or protection changes.

The receiver verifies HMAC-SHA256 over the raw bytes in constant time, accepts at most 1 MB, maps only open goals in the repository from state, and durably retains valid mapped events before returning `202`. Unknown routes/methods return `404`; invalid signatures return `401`; oversized requests return `413`; malformed/unsupported deliveries return `400`. External payloads are wakeup hints. Approval, lane proof, CI, review, merge, build readiness and ancestry are independently read before state advances.

The Mattermost connection uses the [WebSocket API](https://docs.mattermost.com/api/reference/connect-web-socket) authentication challenge. It waits for authentication before readiness. Home-channel post/reaction notifications cause GET reconciliation of actual posts, reactions and bot identities. The socket cannot approve a proposal from its payload. Product's persisted proposal/root identity and a verified person's matching checkmark remain required; bot reactions and replies never count as owner input.

## Delivery and recovery

Events live as immutable private files in `<runtime>/workflow-events/`; consumer receipts live outside that watched directory. The scheduler owns `team-workflow-<teamId>.json`, Product owns `product-workflow-<teamId>.json`, and the Developer owns `goal-workflow-<goalId>.json` after dispatch. Scheduler writes the initial validated brief before `assignGoal` atomically reserves its Developer and approved scope. A restart after assignment re-emits the same dispatch identity without overwriting Developer progress. Redirects and later notifications travel through the inbox.

Each consumer records completion after its finite turn. Redelivery retains the first receipt time; the same event ID with different content is rejected. A crash before the receipt retries the same event, so services reconcile durable state and existing external posts/PRs. Startup always reconciles current external facts, even with no pending inbox files. A disconnected or unauthenticated Mattermost socket fails visibly and releases its resources; restore connectivity and restart the host. There is no reconnection timer or periodic GitHub polling fallback. Inspect failed webhook deliveries and redeliver them in GitHub, or restart to reconcile actual current state.

The Scheduler's primary consumer handles approval, redirects and dispatch only. It is the sole team-journal writer. Each assigned goal has a separate release consumer/receipt and `scheduler-work-<teamId>-<goalId>.json` outbox; vetting has its own consumer and `scheduler-work-<teamId>-vetting.json`. A Developer still implementing without a report needs no release lock. Slow reviews, corrections and retros never hold the dispatch lock or its inbox receipt. Notifications coalesce while an individual consumer is busy; another approval can dispatch immediately on the same host. All consumers are host-owned: one activity lease keeps Supervisor updates at a safe point without serializing the consumers, abort reaches the active runtimes, and shutdown joins all finite turns before releasing that lease. Unchanged work journals do not emit new self-wakeups.

After releasing that activity lease, the Scheduler publishes a durable `queue-changed` hint with ID `scheduler-idle:<teamId>:<sha256>`. The digest binds the sorted completed consumer/event identities for the activity; its receipt time is the fixed epoch. UI hosts opt in and may retry a pending safe update on this prefix. All business consumers receipt-and-ignore it, and an activity with no executed turn emits no idle hint. This makes completion observable after the lock is free without recursively waking business work. The UI capability is absent when there are no goals-v1 teams, preserving the historical UI lifecycle.

`state.json` updates, readiness/update receipts and `builds-in-use` changes produce local wakeups. Inbox receipts and Scheduler/Product/Developer journal writes are excluded from the ingress watch. Awaited Developer subprocess completions return events through the public `DeveloperSeat.turn` result, which the CLI publishes before acknowledging its delivery. The Product CLI publishes a revision-bound candidate event after each completed turn. A turn does not retain a model context; the CLI constructs a fresh service and the next prompt uses current durable facts.

Surfaces receives `uiOptions.workflowEvents(onEvent, signal)` with a separate `ui-<teamId>` consumer. It owns update checks and safe-point reloads. `startup` and verified integration/revert merge events may request `updateCode`; `queue-changed` IDs prefixed `build:` or `running:` request refresh/`checkBuild`, never another update check. This avoids a loop through the updater's own receipt writes. State hints have the prefix `state:`. Aborting the UI lifetime closes all its hosts. The Scheduler waits for the actual running application and bridge receipts; a successful build command alone cannot finish release.

After resolving a recorded blocker, `planning retry --goal GOAL_ID --state PATH` writes a durable finite retry event. It grants no proposal approval and cannot change scope or skip merge protection. Pending CI/review returns to the event boundary. A mechanical integration conflict is handled by a fresh Scheduler resolver in an isolated checkout: merge the observed main commit into the observed sprint head, check both sides of renamed paths against approved scope, push normally, then obtain a fresh bot review and CI for the new head. Out-of-scope or architectural corrections remain explicit blockers. The completed Developer report is not reopened or reassigned.

Correction attempts retain a pinned `integration-recovery-<goalId>-<digest>.json` journal with repository, branch, exact head/base, approved scope, checkout path, decisions and publication status. Partial drafts, blockers, failed checks, unowned edits, unknown process liveness and unverified pushes leave the checkout intact. Retry reuses that same checkout; a committed but unpushed correction is republished without regenerating it. A changed identity/base requires explicit reconciliation, never a reset. The runtime stops only its verified owned processes. Reuse and cleanup additionally require `lsof` on the host to report no open files beneath the checkout; missing/denied inspection fails closed and no foreign process is signalled. Cleanup follows verified publication of the exact two-parent merge, a clean tree including ignored files, and a fresh liveness check. Git removes the worktree without force; the small journal and PR-body artifact remain for recovery evidence.

## Lane interfaces

`DeveloperSeat.turn(event)` returns `{events, report}` and reads the shared goal runtime record. Until that method is installed, CLI dispatch reports the unavailable capability rather than calling legacy `tick`. Product receives `{store, seat, runtime, runtimeFor, chat}`: `runtime` and `runtimeFor` are read-only and project-bound, and `chat` is its authenticated own-bot chat after the existing GET membership check. Product does not need credential code in its queue implementation.

Vetting identities are `proposal-vetted:<proposalId>:<sourceDigest>:<correctedDigest>`. Each digest is lowercase SHA-256 of UTF-8 `JSON.stringify(validateProductProposal(candidate))`. The corrected candidate differs only in vetted `ownedFiles`. Product matches the source digest against its current candidate, applies the returned scope, verifies the corrected digest, and retains the `ProductProposalVetting` provenance. Any later candidate refinement invalidates that vetting. Publication and human approval freeze the full proposal and scope.

The integration report is independently checked against the actual sprint head, merged lane PR heads/merge commits, sprint targets, bot verdicts, CI, ancestry and approved filenames. Release journals record observed conflict pairs, bounded correction runs, and starts of actual protected merge commands. Retros read lane Decisions/Follow-ups from the actual merged PR bodies and shared lane records; they distinguish attempt starts from successful merges. Missing historic invocation timing, tokens or earlier findings remain unknown. Frozen thread content and its sole-file archival PR still require verified delivery, bot review, CI and actual merge before closure.
